# HU-02 - Validacion del plan de pruebas para la API de consultas de cuentas

## Veredicto
**Usable con ajustes.** La historia conecta autorizacion, pruebas funcionales, cobertura y evidencia antes de cerrar el desarrollo de la API de consultas de cuentas.

## Contexto
El componente api (FastAPI) va a exponer endpoints de consulta de cuentas (por ejemplo `GET /api/accounts` y `GET /api/accounts/{id}`), siguiendo el mismo patron de autorizacion por identidad ya usado en `GET /api/tasks`: el owner autenticado solo puede consultar sus propias cuentas. Antes de cerrar el desarrollo se debe validar un plan de pruebas que cubra casos funcionales, de autorizacion y de error, con su evidencia correspondiente.

## Ajustes necesarios
- Definir casos de prueba para que un owner autenticado solo pueda consultar sus propias cuentas (y no las de otro owner).
- Definir casos de prueba para id de cuenta valido, id inexistente (404) y filtros invalidos (400).
- Confirmar que las consultas a la base de datos usan parametros (sin concatenacion de valores de entrada).
- Definir casos de prueba para paginacion o limites de resultados, si el endpoint los expone.
- Documentar las comprobaciones minimas de seguridad: identidad requerida, sin fuga de datos entre owners, sin valores sensibles en logs (numero de cuenta completo, saldo).
- Definir como se mide y reporta la cobertura del codigo modificado (meta: 85% o superior).

## Criterios de aceptacion
- Existe un plan de pruebas documentado con casos funcionales, de autorizacion y de error, cada uno con resultado esperado.
- Las pruebas demuestran que un owner no puede consultar cuentas de otro owner.
- Las pruebas cubren id valido, id inexistente y filtros invalidos con los codigos de respuesta esperados.
- La cobertura del codigo modificado alcanza 85% o superior, con evidencia adjunta.
- No se registran numeros de cuenta completos, saldos ni otros valores sensibles en los logs de las pruebas.

## Evidencia esperada
- Documento de plan de pruebas con casos, resultados esperados y trazabilidad a los criterios de aceptacion.
- Salida/reporte de ejecucion de las pruebas funcionales, de autorizacion y de error.
- Reporte de cobertura del codigo modificado.
- Evidencia de logs redactados (sin valores sensibles) durante la ejecucion de pruebas.
