## Contexto

La matriz de hallazgos indica que el token se representa como Base64 de campos separados por `|`, comprueba un secreto compartido y su expiración, pero no verifica una firma criptográfica. También indica que `legacy_identity` acepta un token Base64 con secreto hardcodeado y sin firma, lo que permite falsificar el username y superar el control de autorización de propietario.

## Ajustes necesarios

- Evitar que se acepten tokens cuya autenticidad no pueda verificarse criptográficamente.
- Asegurar que la identidad utilizada para autorizar el acceso a tareas provenga de un token auténtico y no pueda alterarse para eludir la comparación de propietario.

## Criterios de aceptación

- Una prueba con un token cuya identidad o rol haya sido alterado verifica que la autenticación lo rechaza.
- Una prueba con un token falsificado para representar a otro propietario verifica que no permite eludir la autorización por identidad.
- Una prueba de autorización verifica que una identidad autenticada distinta del propietario recibe una respuesta `403` al acceder a tareas de ese propietario.

## Evidencia esperada

- Resultados de pruebas automatizadas para tokens alterados o falsificados y para la autorización entre identidades distintas.
- Cambios revisados en las líneas de código referenciadas por H-API-01 y H-API-02.
